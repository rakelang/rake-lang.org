GPU profiles

Rake doesn't have a GPU compiler, runtime or device-artifact verifier yet, because CPU coverage and native C interoperation come first. In this design, the hardware schedules warps while Rake controls the algorithm's lane mapping, keeps temporaries in registers where the profile requires it, and makes memory and synchronisation costs explicit. The first backend will target NVIDIA PTX and verify an ahead-of-time cubin.

Racks and lanes

A CPU rack occupies one vector register, whereas a GPU rack will span a specified warp, wave or subgroup, with each invocation holding one lane's value, as in NVIDIA's SIMT model. A hidden loop that processes every rack element inside one invocation breaks the profile's rules.

Partial masks are legitimate program choices, and Rake can't make arbitrary inputs keep every lane active. It can tell uniform control from lane-varying control, though, and refuse serialization introduced by the compiler.

First profile: NVIDIA PTX

The proposed profile, nvidia-ptx-sm120, fixes PTX ISA 8.7, sm_120, 64-bit addressing and a 32-lane rack, and initially supports only that SM architecture. It uses CUDA 12.8.1, with the exact tool binaries pinned by hash. Other architectures and operations need a checked profile extension, and the compiler will report an unsupported construct's source location, profile and failed obligation.

Every launched warp will contain 32 invocations. Padding invocations stay present until the required collectives finish, supplying neutral operands for inactive data lanes, and never touch out-of-bounds records. Every participant reaches the same collective with the same membership mask. Execution never relies on implicit lockstep between threads, so the checker will reject reads from unavailable shuffle sources, and any collective when it can't establish which lanes take part.

Compilation and final-code verification

Rake source and GPU lane contract
  -> checked IR: uniformity, masks and memory effects
  -> inspectable PTX 8.7 for sm_120
  -> pinned ptxas: ahead-of-time cubin
  -> nvdisasm and cuobjdump: instructions, control flow and resources
  -> Rake's sm_120 artifact verifier
  -> exact verified cubin loaded by the runtime

NVIDIA owns final instruction selection, physical register allocation and instruction scheduling on this virtual profile, so Rake verifies the resulting artifact instead. Using NVIDIA's binary utilities, the verifier will inspect every reachable instruction and control-flow path, relate register and data flow to the profile's lane, mask, memory and collective rules, and check the LOCAL and STACK resource counts. It rejects unknown instructions, opaque helper paths and unexplained loops, and rejects the artifact whenever the evidence is insufficient. Designated pure regions forbid spills, reloads, calls and hidden serial lane loops, while explicit address and traversal work has separate obligations.

Artifact identity and runtime boundary

Verification will bind the exact cubin and kernel hashes to the source, profile, compiler revision, PTX hash, toolchain binaries and flags, target SM, verifier version and launch/parameter ABI, and runtime evidence also records the device and driver. A driver or runtime change requires refreshed compatibility checks and execution evidence. The runtime will load only those verified bytes, and refuse PTX JIT fallback or a rebuild with different flags.

The host interface is a separate C ABI for loading a verified artifact and launching a kernel with an explicit CUDA context, stream and versioned parameter layout. Column arguments will be device addresses with counts and alignment requirements, and the caller owns allocation, lifetimes, stream ordering and synchronisation, and launch errors stay visible to it. CUDA supplies the execution interface, while Rake source compiles directly to PTX.

More registers per thread can leave room for fewer resident warps, as NVIDIA's register and occupancy discussion explains. A strict no-spill profile will still reject a forbidden spill when another policy might run faster, and a relaxed resource policy will get a profile of its own.

Verification tests

Independent numerical and CPU reference results will check lane mapping, mask priority, tails, collectives and floating-point edge cases, including empty data, partial warps, missing participants and unavailable shuffle sources. Negative fixtures will give the verifier each forbidden pattern, including incorrect address patterns and unexpected divergent control, and it refuses them even when a resource summary looks acceptable. Artifact checks will alter bytes, architecture, flags and launch metadata, so verification can't silently carry over to a different kernel.

Later portable and physical profiles

A later SPIR-V/Vulkan profile, such as vulkan-subgroup32 or vulkan-subgroup64, will span a rack across a required subgroup width rather than a large OpTypeVector inside one invocation. Each will specify its SPIR-V and Vulkan versions, memory model, numerical modes, operations and collective participation, and pipeline creation will reject incompatible devices. Physical resource verification needs the driver-generated executable, and Vulkan's optional pipeline executable properties extension may expose it. Rake refuses certification without enough final-code evidence, and binds that evidence to the module, pipeline state, device, driver and verifier.

A physical profile for a sufficiently documented ISA, such as one in AMD's architecture documentation, would let Rake own selection, allocation and scheduling as well as verification.
